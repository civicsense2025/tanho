# Lamina Platform REST API v1

A versioned REST API for external clients (the Lamina Swift app, scripts, integrations). Authenticates via bearer tokens minted in the admin panel. Every endpoint returns the same discriminated-union envelope as the server actions:

```json
{ "ok": true, "data": { ... } }
{ "ok": false, "error": "Human-readable message" }
```

## Authentication

### Bearer tokens

1. An **owner** signs into their self-hosted Lamina instance in a browser.
2. Visits **Admin → Settings → API tokens** and mints a token (named, e.g. "My iPhone app").
3. The raw token (`lamina_<43 chars>`) is shown **once** — copy it immediately.
4. The external client sends it as `Authorization: Bearer lamina_<...>` on every request.

Tokens carry the **owner's full authorization surface**. The user's existing role (owner/editor) determines what each token can do — `requireApiUser(role?)` enforces the same gates as the cookie-based `requireUser(role?)`. Only owners can mint tokens.

### Security model

- Only the SHA-256 hash of the token is stored (`api_tokens.token_hash`) — a DB leak alone can't forge a token.
- `lastUsedAt` is stamped on every request for hygiene.
- Tokens have no expiry by default; owners can revoke at any time.
- HTTPS is required in production (the platform enforces `Secure` cookies; bearer tokens should never transit plain HTTP).

## Status codes

| Code | Meaning |
|------|---------|
| 200 | Success |
| 201 | Created |
| 400 | Validation error (envelope `error` has the message) |
| 401 | Missing/invalid/expired token |
| 403 | Valid token but role insufficient (e.g. editor calling an owner-only endpoint) |
| 404 | Resource not found |
| 409 | Conflict (e.g. duplicate route, cannot fulfill a refunded order) |
| 413 | File too large |
| 415 | Unsupported media type |
| 429 | Rate limited |
| 500 | Internal server error (details never leaked) |

## Connection model for external clients

Lamina is **single-site per deployment** — each self-hosted instance is one site. A client connects to one instance at a time:

1. User enters their **instance URL** (e.g. `https://my-site.com`).
2. Client opens the instance's `/admin/settings/api-tokens` in a browser so the owner can mint a token.
3. Owner pastes the token back into the client.
4. Client validates with `GET /api/v1/me` — on `200`, save the site (URL + token) and construct all future requests as `{instanceUrl}/api/v1/*` with the bearer header.

Multiple sites can be stored; the user switches between them. Tokens are stored client-side in the platform keystore (Keychain on Apple platforms) — never in plaintext or logs.
